## Working rules (from the brief)

- Work phase by phase (BRIEF.md §11). Before each phase, propose the plan and wait for the owner's OK.
- Ask the owner before adding a paid service, storing a new kind of personal data, or departing from the brief.
- Every external service sits behind an adapter in `src/adapters/` with a mock or manual implementation, so the app runs end to end with no paid accounts.
- Never commit secrets. Keys live in `.env.local`; keep `.env.example` current.
- Keep `PROGRESS.md` current (done, next, decisions, open questions). Commit in small working steps.
- The owner is not a developer. When they need to do something (create an account, add a key), give numbered, plain-English steps, and never ask them to paste keys into chat.
- Australian English and formats: dd/mm/yyyy, AUD, +61 phone numbers. Store times in UTC; show a shift's times in its site's time zone, and everything else in Australia/Sydney.

## Conventions

- **Database:** Supabase Postgres. Schema changes are SQL migrations in `supabase/migrations/` and are never edited once pushed; add a new migration instead.
  - RLS is enabled on every table.
  - The hosted project does **not** auto-grant new tables to the API roles, so every migration grants explicitly (`anon`, `authenticated`, `service_role`).
  - RLS tests live in `supabase/tests/`.
  - The hosted dev project's sign-in settings are in `deploy/muster-dev/supabase/config.toml`, pushed by the database workflow with `supabase config push` (which changes only what that file declares). Keep it in step with `supabase/config.toml`.
- **Scheduled jobs:** pg_cron calls `call_scheduled_job()`, which posts to `/api/cron/<job>` through pg_net with the `CRON_SECRET`. The site's address and the secret are in Vault, saved by the database workflow with `set_scheduled_job_target()`; where they aren't set (locally, CI), the jobs do nothing. Change a schedule with a new migration.
- **Live site and releases** (owner, 03/11/2026): www.shifta.com.au runs on its own Supabase project and Vercel project with demo mode off, and the demo moves to demo.shifta.com.au. The live site changes only when the owner says "release": the tested commit goes to `main`, and `.github/workflows/live-deploy.yml` migrates the live database, pushes its sign-in settings (`deploy/shifta-live/`), loads the real setup (`npm run seed:reference`, never demo data), then builds the site. A migration must work with the site version before it. Steps are in `docs/launch.md`.
- **Records:** archive (`archived_at`), never hard-delete personal or employment records.
- **Money:** integer cents.
- **Time:** `timestamptz` in UTC; convert with the helpers in `src/lib/format.ts`. Shift times (screens, messages, timesheets, invoices and the payroll file) use the site's zone, `zoneOf(state)`: the functions that list shifts and timesheets return the site's `state`, and `shiftHours()`, `shiftSummary()`, `hoursLabel()`, `timeInputValue()` and `TimesheetDetails` require a zone. Hours typed into forms are read on the site's day (`shiftDay()`). Our team's screens add `zoneNote()` (" (Perth time)"). A worker's own settings (quiet hours, availability) follow their home state. Everything else, including pay weeks, is Sydney time.
- **Business rules** (eligibility, pay/bill, hours, expiry, reliability) live in `src/domain/` as pure functions with Vitest tests next to them. Price shifts with `loadPricing()` (`src/server/pricing.ts`), which feeds `splitShift()` and `costShift()` in `src/domain/pay.ts`.
- **Rate cards and award rules** (owner, 01/11/2026): a card can hold its award's rules as data, never code (brief §4.8): overtime after `overtime_after_hours` (blank: the setting), the later overtime and Saturday rates after `tier_hours`, Saturday's later rate from a time, weekday ordinary hours (time outside them is overtime), and whole-shift early or late and night shift loadings (`AwardRules` in `src/domain/rates.ts`). With them, `splitShift()` pays each minute at the highest rate that applies; pass the card (`rules.card`, or the booking's `cost_rules.card`) wherever a shift is split. Rates kept with bookings made before them have no `award` and split the old way. Overtime is priced without super (owner, 03/11/2026): a card lists the rate types its award makes overtime (`super_free_types`, overtime at both rates by default), and `onCostPctFor()` leaves super off them for rules that carry `superPct`. A work type's long service levy (`categories.long_service_levy_pct`: 1% for commercial and builders cleaners, NSW's contract cleaning scheme; owner, 14/11/2026) is an on-cost on ordinary pay only: rules carry it as `levyPct`, and `ordinaryOnlyPct()` (super plus the levy) is what's left off super-free types and allowances. A card's allowances (`allowances`: each shift worked; once a day, with the worker's first-booked shift that day, `each_day` and `ShiftFacts.earlierShiftToday`; or overtime past the booked finish over some hours, `allowancesFrom()`) are priced into the booking's rules with their charge (no super or levy), earned in `costShift()` (`ShiftFacts.lateOvertimeMinutes`, from `costTimesheet()`), and appear on estimates, invoice lines, the payroll file (from the hours' costing) and the worker's pay (`my_timesheet_pay()`); a late cancellation earns none. Bill rules can fix a rate for each new rate type, or fall back (`BILL_FALLBACK`). The launch work types' cards (each award's casual rate plus $0.50, checked by the owner's accountant) are in `AWARD_RATE_CARDS` (`scripts/seed/data/rates.ts`), which the seed adds once each; admins change them in Admin → Rates. The margin is a setting the owner enters: never put it in code or docs, as the repository is public.
- **Overtime across a worker's shifts** (owner, 02/11/2026): a worker's hours with us add up across the day and the week (`weekly_overtime_after_hours`, 38, Monday to Sunday), counted in the order their shifts were booked (`src/domain/overtime.ts`). `splitShift()` takes their earlier hours as `prior`, so the business whose booking takes them past a limit pays the overtime. `costTimesheets()` costs a worker's week together (paid hours are locked and skipped), and the pay run costs the week's owed hours again before planning (`owedTimesheetIdsWith()`). `jobs.allow_overtime` (a box when posting first-in work, off unless ticked) decides whether a worker whose other shifts would put a first-in shift or call-out into overtime may take it: matching marks them `overtime`, and `book_worker()` refuses with `overtime_from_other_shifts()`. Businesses see it on applicants and booked workers, and workers on their booked shifts (`OvertimeNote`), from `src/server/overtime.ts`. `worker_booked_minutes()` gives the hours, to the service role only.
- **Data access:** user-initiated reads and writes use the signed-in user's Supabase client, so RLS applies. Use the service-role client only in:
  - cron jobs, seeding, the deploy check of sign-in codes (`scripts/check-sign-in-codes.ts`) and audited admin actions
  - recording agreement acceptances (`src/server/agreements.ts`, so the IP address comes from the server)
  - the live site's send hooks for sign-in codes (`src/server/auth-hooks.ts`), which Supabase Auth calls signed: counting each person's code texts
  - creating a business from the ABN register's details, and checking an ABN isn't already registered (`src/app/business/onboarding/actions.ts`)
  - sending notifications (`src/server/notifications.ts`): who to tell, their devices, preferences and admins' template wording
  - reading rate cards and bill rules to price shifts, which work types have rates, and the website's example pay (`src/server/pricing.ts`); callers only get the result
  - working out overtime from a worker's other shifts (`src/server/overtime.ts`), from their hours with us and the shift's rates; callers check the person may see the shift and only get the hours and the money
  - matching workers to shifts and texting urgent call-outs (`src/server/matching.ts`, which runs `src/lib/matching.ts`)
  - messages about bookings and reminders (`src/server/booking-notices.ts`, `src/server/reminders.ts`), and scheduled jobs in `src/app/api/cron/[job]/`, which need the `CRON_SECRET`
  - working out reliability from bookings (`src/server/reliability.ts`), and flagging possible no-shows (`src/server/attendance.ts`)
  - costing approved hours (`src/server/timesheets.ts`, which runs `src/lib/timesheet-costing.ts`) and messages about timesheets (`src/server/timesheet-notices.ts`)
  - the weekly pay run (`src/server/pay-runs.ts`, which runs `src/lib/pay-runs.ts`): previewing and saving runs, making and emailing invoices and overdue reminders, and making and emailing a credit note once an admin has issued it (`src/server/credit-notes.ts`)
  - the compliance job (`src/server/compliance.ts`, which runs `src/lib/compliance.ts`): expiring tickets and visas, and checking bookings again
- **Reading many rows:** the database API returns at most 1,000 rows a request and doesn't say when it stops there. Jobs that read a whole table page through it with `allRows()` (`src/lib/supabase/all-rows.ts`), ordered by id.
- **UI:** shadcn/ui-style components in `src/components/ui/`, written by hand on Radix (`radix-ui` package) because the shadcn registry is blocked from the cloud container. Mobile-first for workers, large tap targets, one main action per screen. Worker forms use `NativeSelect` rather than the Radix select. A form that only works with JavaScript waits for `useHydrated()` (`src/lib/use-hydrated.ts`), as sign-in does, so an early tap can't reload the page with what was typed in the address.
- **Look:** colours are tokens in `src/app/globals.css`; the blue primary and hi-vis orange accent come from `src/config/brand.ts`, with `deep` (headlines, footer, dark bands) and `primary-soft` (light blue bands). Pages sit on a light page colour (`bg-background`); anything boxed on it (cards, lists, fields, tables) is `bg-card`, and tables are framed unless `bare`. Public pages are full width: bands of colour edge to edge, content in `Container`, and a `PageBand` title on inner pages. The font is Figtree (`@fontsource-variable/figtree`, bundled, so builds need no network). The logo is the wordmark, "shifta" in lower case with a hi-vis dot on the i (`Wordmark` in `src/components/layout/brand-mark.tsx`, drawn in `src/config/logo.ts`; owner, 01/11/2026); it takes the text colour. The S icon (`logo` in the same file) is only the app and browser-tab icon; after changing it or the colours, run `npm run icons`. Public pages read industries through `listIndustries()` (`src/server/industries.ts`). The home page leads with our core service, fast on-demand general and skilled labour; call-outs are an add-on further down (owner, 01/11/2026). Its sections and the industry pages' branded features (`src/components/home/`) must only describe what the app really does. Pictures of the app carry no "Example" labels (owner, 01/11/2026): their people (`src/components/home/people.tsx`) are illustrative, which the footer says, and their figures follow the current rates and settings (the pay is a restoration technician's current rate, from `standardWeekdayPay()`; call-out pay and alert minutes are read from settings). A person's photo goes in `public/people/` only when we have the rights to it; until then their avatar shows initials. The site has no made-up testimonials, client logos or statistics.
- **Navigation:** in signed-in areas nothing hides behind a menu button: they have a sidebar from tablet width (`md`); on phones, workers get tabs along the bottom plus a row of the other pages under the header (`worker-nav.tsx`), and business users and admins get a row of every page (`ConsoleStripNav`). Sign out is in that row, the sidebar, and the worker's Settings. The public site has a menu button on phones and tablets (`PublicMenu`; owner, 01/11/2026): Sign in, Register (opening to business or worker) and the site's pages.
- **Loading:** links swap pages in without a full reload, so the browser shows no loading of its own. `NavigationProgress` (root layout) shows an orange bar while the next page loads, and the worker, onboarding, business and admin areas each have a `loading.tsx` showing `PageSkeleton` at once. Pages there stream, so a `notFound()` or `redirect()` after the first `await` can't change the status code; call them first where the status matters. In browser tests the address changes while the outline still shows, and a full load reveals the page a moment after `goto()` returns: check for something on the page, or call `pageLoaded()` (`e2e/helpers.ts`), before checking that something isn't there or reading a list with `.all()` or `.count()`.
- **Long text** (agreements, contracts) scrolls inside `ScrollBox` (`src/components/scroll-box.tsx`), which keyboard users can reach. `expectAccessible()` in browser tests also fails a page that scrolls sideways, so let long emails wrap (`[overflow-wrap:anywhere]`).
- **Sign-in and registering:** everyone signs in and up with an email code or the emailed link (`src/app/(auth)/login/`, `src/server/email-codes.ts`); there's no sign-in by mobile (owner, 31/10/2026). Registering (`src/app/(auth)/register/`; owner, 01/11/2026) is a short form, then the same code: workers give their name and email, businesses add a mobile and their ABN. What they typed is kept with the account until the code is in and read with `signUpDetails()` (`src/server/sign-up.ts`); people can change it, so check it again before use. There's no password and no "How did you hear about us?". On the live site, Supabase Auth first checks a Cloudflare Turnstile token (`useBotCheck()` shows the check when `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is set, and its token goes with the code request as `captchaToken`), then hands every code to the app's send hooks (`src/app/api/auth/hooks/[kind]/`, signed with `AUTH_HOOK_SECRET`; `deploy/shifta-live/supabase/config.toml`). They send only what `src/domain/auth-messages.ts` allows, with fixed wording: sign-in codes by email, and texts only to confirm a new Australian mobile, five a day per person (`auth_texts`). There's no sign-in by text and no changing an email address there, as Supabase's bot check doesn't cover a signed-in person's own changes.
- **Worker area:** `src/app/worker/(app)/` has the tabbed app; `src/app/worker/onboarding/` is the wizard, whose step pages also serve as edit pages once a worker has submitted (`StepFrame`, `StepActions`). After registering, the quick sign-up (`onboarding/start/`; owner, 01/11/2026) confirms their mobile with a texted code and takes their suburb, travel distance and work types, records the collection notice and sets availability to any time (`QUICK_START_STEPS`, `quickStartDone()`). Then the home screen shows "Get ready to work" (photo and ID, right to work, tickets, paperwork, in `ONBOARDING_STEPS` order) and shifts near them.
- **Admin access:** admin pages and actions call `requireAdmin()` (role plus authenticator app; the database's `is_admin()` checks the same). Log views of worker documents with `logAccess()` (`src/server/audit.ts`).
- **Business area:** `getMyBusiness()` (`src/server/businesses.ts`) returns the signed-in person's business and role, and joins them to a business they were invited to. Owners and managers run the account (`canManage()`); only owners change the team and billing details; supervisors see only their sites. Sign-up is one screen (`/business/onboarding`, `setUpBusiness()`; owner, 01/11/2026): the business from its ABN, the billing contact from the owner's details, the services agreement, then `submit_business()` and an `admin_business_submitted` alert to our team. Sites are added in the post-work steps (the inline `SiteForm`). While we check them, businesses can set up shifts (`draftingBlocker()`) but not post them (`postingBlocker()`).
- **Posting work:** the steps in `src/app/business/post/[id]/` load the draft with `loadDraft()` (pages) or `draftForAction()` (actions) from `src/server/jobs.ts`, and end with `finishPostStep()`. Only the `post_job()` database function makes a job live; `duplicate_job()` copies one for templates and "Post again", whose shortcuts (templates and recent different jobs) come from `src/components/jobs/quick-post.tsx`. Every job has a number (`jobs.number`, an identity column nobody sets or changes) and can carry the business's PO or reference number (`po_number`; owner, 04/11/2026), set on the review step or later through `set_job_po_number()` (owners and managers); `duplicate_job()` leaves it out. Job photos go in the `job-photos` bucket, in a folder named after the business.
- **Industries:** work types (`categories`) belong to an industry (`industries`, admin-managed, public to read; none means "other work"). Group them with `groupByIndustry()` (`src/lib/industries.ts`) wherever people choose work; an industry's icon name maps to an icon in `src/config/industry-icons.ts`.
  - **The focus** (owner, 02/11/2026) is four industries and nine work types: general labourer; commercial and builders cleaner; restoration labourer (the cleaning award's level 1, for labouring; back on 04/11/2026) and restoration technician (level 2, for certified work), both with a White Card, and jobs ask for IICRC tickets themselves; and pick-packer, storeperson, forklift driver and removalist offsider. The rest are archived, never deleted (`archived` in `scripts/seed/data/catalogues.ts`; migration `20261102020000_focus_work_types.sql` for an existing database).
  - Non-admins can't read archived work types, so an embedded `categories(...)` comes back null for them: treat that as no longer offered (`quick-post.tsx`, the worker profile, `onboardingSnapshot()`).
  - A work type can be posted only once it has a rate card, which `workTypesWithRates()` (`src/server/pricing.ts`) says: the post-work step shows the others as "coming soon" and refuses them, the industry pages say so (`PublicWorkType.bookable`), and the home page lists only bookable work. Placeholder cards (`DEFAULT_BASE_RATES_CENTS`) are only for focus work types that also have checked ones; the warehouse three wait for the Storage Services and Wholesale Award's rates.
- **States:** every state and territory is a row in `jurisdictions`, and admins open each one for work (`open_for_work`). `state_blocked()` (used by `post_job()` and the review step) blocks work in a state that isn't open, or that needs a labour hire licence we don't hold. Pricing, matching and costing use the site's state time zone (`STATE_TIME_ZONES` in `src/domain/pay.ts`). The website talks about Sydney only for now (`brand.area`; owner, 31/10/2026): no state-by-state or city pages. The demo address lookup uses `src/data/suburbs.ts`; suburb names repeat across states, so pass the state to `findSuburb()` when you have it. Tickets each state issues itself (RSA, working with children checks, traffic control) have a version per state (`credential_types.state`, sharing a `family`): jobs take their site's state's version and workers are asked for their home state's, through `ticketForState()` and `heldInState()` (`src/lib/state-tickets.ts`); the website names them by family. Public holidays are entered per state in Admin; the States page warns about an open state with none.
- **Matching:** `matchPostedJob()` and `refreshWorkerMatches()` (`src/server/matching.ts`) save each worker's eligibility for open shifts in `shift_matches`, using the rules in `src/domain/eligibility.ts`. Workers read their offers only through `my_shift_offers()` and `my_job_offer()`, which leave out the address and report-to details; businesses get `job_offer_count()`. Workers we haven't checked yet see `preview_shift_offers()` instead (owner, 01/11/2026): open shifts in their work types within their travel distance, with the pay, but no business, address or way to apply, and nobody is told about them. Call `refreshWorkerMatches()` after anything that changes what a worker can take.
- **Call-outs** (`jobs.type = 'urgent'`): first in, and opted-in workers hear by text and app notification at any hour. Pay and charge loadings come from the `urgent_loading_pct` setting (20% and 20%). `make_callout()` turns posted work starting within 48 hours into a call-out, then call `matchPostedJob()` to price and announce it. The `callouts` job runs `flag_unfilled_callouts()` every five minutes, and `notifyCalloutUnfilled()` tells the business and admins once `callout_alert_minutes` has passed. Businesses see how many workers a call-out reached through `job_callout_reach()`.
- **Bookings:** workers apply or accept, and businesses pick, only through the database functions `apply_for_shifts()`, `accept_shifts()`, `withdraw_applications()` and `book_applicant()`, which all book through `book_worker()`; it locks the shift and copies the shift's priced terms into `assignment_rates`. Workers read their shifts and jobs through `my_shifts()` and `my_job()` (the address only once booked); businesses read `job_applicants()` and `job_bookings()`. Applying can carry a note (`apply_for_shifts(p_note)`, changed with `set_application_note()`); notes and the worker's bio follow `workerWordsProblem()` (`src/domain/worker-words.ts`) and the database's `worker_words_ok()`: short, and no phone numbers, emails or links.
- **Cancellations and no-shows:** only through `cancel_my_bookings()` (workers), `cancel_shifts()` (owners and managers), `admin_cancel_booking()` (our team: status `cancelled_by_admin`, no penalty or charge) and `report_no_show()` (anyone at the business who can see the job), which read their thresholds with `setting_numeric()`. After any of them, call `refreshReliability()`; rules are in `src/domain/reliability.ts`.
- **Admin console:** lists and reports read through admins-only functions: `admin_worker_list()`, `admin_shift_board()`, `admin_report_summary()`, `admin_report_breakdown()`, `admin_sales_lines()` and `admin_audit_log()`. Payroll tax is 0% in prices until wages near NSW's threshold (owner, 14/11/2026): the dashboard warns from the saved pay runs (`payrollTaxWarning()` in `src/domain/payroll-tax.ts`, the `payroll_tax_threshold` setting). Filters live in the page address (`src/lib/search-params.ts`); key filter forms by their values so a link that changes them resets the fields.
- **Admin queues:** matters are `admin_flags`, settled only through `settle_admin_flag()` with a note (the decisions open for each kind are in `src/lib/admin-flags.ts`); hours queries go through `resolve_timesheet()`. Possible no-shows settle themselves on a clock-in, a confirmed arrival or a no-show report.
- **On the day:** attendance is append-only `attendance_events`, added only through `clock()` (workers) and `confirm_arrival()` (the business); `attendanceOf()` in `src/lib/my-shifts.ts` says where a worker is up to. Safety reports go through `report_safety_issue()`, with photos in the `safety-photos` bucket.
- **Timesheets:** the database makes them, at clock-out (a trigger on `attendance_events`) or with `record_missing_timesheets()` for a missed clock-out; once one exists, attendance is closed. They change only through `approve_timesheets()`, `adjust_timesheet()`, `add_timesheet()`, `dispute_timesheet()`, `note_timesheet()`, `resolve_timesheet()` (admins) and `auto_approve_timesheets()`. Read them through `my_timesheets()` (with the worker's pay) and `business_timesheets()` (with the charge); workers see how their pay adds up, a line per rate with overtime and any call-out loading, through `my_timesheet_pay()` (pay only, never the charge; `PayBreakdown`). After hours are approved or changed, call `costTimesheets()`, which saves `timesheet_costs` from the booking's rates, and `refreshReliability()` if the start moved: a booking counts towards reliability once its hours are in.
- **Ratings:** only through `rate_worker()` and `rate_site()`, once each per booking after the hours are approved; they keep the averages on `workers` and `businesses`. Tag codes live in `src/domain/ratings.ts` and in those functions. Favourites and blocks change through `src/server/business-workers.ts`, which refreshes matches. Workers see each business's average through `my_shift_offers()` and `my_job()`. Businesses see a worker's profile (`/business/workers/[id]`) through `business_worker_profile()`, only for workers who've applied to or worked for them, or that they have as a favourite or blocked; badges come from `workerBadges()` (`src/domain/worker-badges.ts`).
- **Pay runs:** each week (Monday to Sunday, Sydney) is run once, in order, by `runPayRun()` in `src/server/pay-runs.ts`: an admin from Pay runs, after checking each invoice's lines ("Issue invoices and payroll file"). On the run day (Wednesday) the `pay-run` cron job only tells admins the week is ready (`admin_pay_run_ready`) and the dashboard shows "Pay run to check" (`runDayReached()`); with the `pay_run_automatic` setting on, it issues the run itself (owner, 14/11/2026). The app names no payroll provider: the owner is still choosing one. `planPayRunWith()` (`src/lib/pay-runs.ts`) lines up what `pay_run_candidates()` says is owed: approved hours as costed, and late cancellations priced by `costCancellation()` (`src/domain/pay-runs.ts`). Only `save_pay_run()` saves a run; it checks every line again and numbers the invoices, and a trigger locks paid hours. Each line keeps the job and PO numbers and the award and level of the booking's rate card (`rate_cards.award`), which `save_pay_run()` takes, and a row per rate (`parts`, from `invoiceParts()` in `src/lib/pay-run-format.ts`; owner, 04/11/2026) that must add up to its charge; lines saved before have none and show their detail text. Invoice PDFs come from `src/lib/invoice-pdf.tsx` (@react-pdf/renderer, text through `pdfText()`), go in the private `invoices` bucket as `<business id>/<number>.pdf`, and are emailed with the PDF attached; `finishInvoices()` retries any that weren't. The PDF library is ESM-only, so `tsx` scripts like the seed can't render PDFs (the app and Vitest can). Businesses read invoices through RLS (owners and managers) and their lines through `invoice_lines()`, never the pay; admins mark them paid with `mark_invoice_paid()` and `mark_invoice_unpaid()`. The payroll file is `payrollLines()` through the payroll adapter. An invoice that's gone out never changes: our team corrects it with a credit note (`issue_credit_note()`, admins only), which takes the invoice's GST in proportion and lowers what's owed (`credited_cents`); an unpaid invoice credited in full is `credited`. Its PDF and email follow the invoice's (`src/server/credit-notes.ts`). The `invoice-reminders` job emails overdue reminders (`sendInvoiceReminders()`, `reminderDue()`) and finishes any credit note not yet sent. The sales and GST report (`/admin/sales`) reads `admin_sales_lines()`. Spreadsheets write text people typed through `csvText()` (`src/lib/csv.ts`), so it can't run as a formula.
- **Notifications:** every message goes through `notify()` (or `notifyAdmins()`, `notifyBusinessOwners()`, and `emailTemplate()` for an address that isn't a user or an email whatever the person's settings, like the copy of the Fair Work statements after the paperwork step, `fair_work_statements` with links from `src/config/fair-work.ts`) in `src/server/notifications.ts`, using a template from `src/config/notifications.ts`. Admins can change a template's words, so pass values rather than building text, and keep `{{link}}` at the end of worker messages. Channels, preferences and quiet hours are in `src/domain/notifications.ts`. Pass a `dedupeKey` for anything a job might send twice. Web push needs `PUSH_PROVIDER=webpush` and VAPID keys; in the demo a stand-in device writes to the outbox. Browser tests turn quiet hours off (`e2e/global-setup.ts`).
- **Compliance:** the hourly `compliance` job (`src/server/compliance.ts`) warns about and expires tickets and visas (rules in `src/domain/expiry.ts`), tells admins about VEVO re-checks due, and flags booked shifts that no longer pass the rules as `booking_at_risk` admin flags. It also emails casuals the Casual Employment Information Statement again at 6 months, 12 months and every year after, counted from activation (`casualStatementDue()` in `src/domain/casual-statement.ts`), recording each in `casual_statement_reissues` before sending (owner, 14/11/2026).
- **Uploads:** browser to private storage via `FileUpload` (`src/components/forms/file-upload.tsx`), in a folder named after the worker's id. Server actions accept a path only through `acceptedUpload()` in `src/lib/uploads.ts`.
- **Agreements:** versions in `agreements`; published wording never changes, so a change is a new version, which the seed (`scripts/seed/data/agreements.ts`) adds once. A `-draft` version never displaces the current one; an approved version (no `-draft`) takes over from a current draft (`set_current_agreement()`); demo businesses accept the current services agreement, and demo workers who accepted an earlier version of a document accept its current one. Approved (1.0; owner, 14/11/2026): the services agreement, the casual contract, the privacy collection notice (and the privacy page, `LegalPage`) and the two Fair Work statement pages. Still drafts: the website's terms of use (`DraftPage`) and the South Australian notice.
- **Brand:** the product name lives only in `src/config/brand.ts`.
- **Tests:** `docs/testing.md` maps the brief's flows to the browser tests. The Phase 1 acceptance run (`e2e/acceptance/`, its own Playwright config and CI job) takes 3 businesses and 10 workers from sign-up to the payroll file and invoices through the app; its only database change is moving the booked shifts back to last week. When a flow's screens change, update its steps in `e2e/acceptance/flows.ts` too.
- **Adapters:** each outside service lives in `src/adapters/<name>/` as a typed interface, a mock or manual implementation, and a `get<Name>()` factory.
  - Mocks for email, SMS and push write to `dev_outbox`.
  - The ABN adapter has a live implementation (free ABR service), used when `ABN_LOOKUP_GUID` is set.
  - Real providers the owner approved (03/11/2026): Resend (`EMAIL_PROVIDER=resend`), Twilio (`SMS_PROVIDER=twilio`, sender "Shifta"), Google Places (`GEOCODER_PROVIDER=google`) and web push. The live site won't build with a mock or a missing key (`liveSetupProblems()` in `src/lib/live-setup.ts`, run by `next.config.ts`).
  - Add another paid provider only after the owner approves it, selected by its `*_PROVIDER` env var.

## Cloud container notes

- The Docker daemon may not be running. Start it with `dockerd > /tmp/dockerd.log 2>&1 &`.
- Image pulls for local Supabase can fail:
  - `public.ecr.aws` (the default registry) with "Data limit exceeded".
  - Docker Hub with "429 Too Many Requests".

  What works: set `SUPABASE_INTERNAL_IMAGE_REGISTRY=docker.io` for every `supabase` command. For any image Docker Hub refuses, run `docker pull mirror.gcr.io/supabase/<image>:<tag>`, then `docker tag` it to `supabase/<image>:<tag>`. `npx supabase services` lists the tags; `pg_prove:3.36` and `postgres-meta:<tag>` are needed for `test:db` and `db:types`.
- Postgres grants EXECUTE on new functions to PUBLIC by default. The base migration revokes that globally; `supabase/tests/database/00_security_baseline.test.sql` fails if any function becomes callable by `anon`.
- `ui.shadcn.com` and `abr.business.gov.au` are blocked by this environment's network policy. Components are hand-written; the live ABN adapter can only be exercised from Vercel or once the owner allows the host.
- Playwright browsers are pre-installed for `@playwright/test@1.63.0`. Keep that exact version unless you also install browsers.
